# LoveLab 产品需求与开发计划

版本：V1.3 草案  
更新日期：2026年10月3日  
阶段：前端试玩已实现，后端API已开发，账号UI、页面云同步和内容管理UI待接入  
读者：项目负责人、设计、前后端开发与内容编辑

本文定义 LoveLab 首版范围、玩法、内容规则、页面、架构及开发验收标准。首版采用前后端分离，面向男生认识女生、表达好感与经营关系的实际情景，通过轻松搞笑的视觉小说和选择题提供学习体验。先验证好玩与有用，再扩展商业功能。

本文的数量、周期和指标是项目规划假设，不代表已完成的功能或已有用户数据。

本版结合狗头军师 Skill 的证据分级、关系启动、沟通与实用指南，定义可复用的内容能力包。Skill 用于编辑制作与审核题目，网站运行时读取审核后的剧情数据。用户入口仍是小游戏和手册，不增加关系建档问卷或对话窗口。

## 1 产品定位与目标

产品定位：轻喜剧恋爱闯关网站。

对外表达建议：在游戏里先尴尬一次，现实里少尴尬一点。

用户通过看情景、选行动、看后续、读解说、尝试另一条路线，练习认识、聊天、邀约、约会和关系沟通。界面以选项与文档为主，首版不提供实时 AI 对话。

首版目标：

- 用户无需注册即可开始一局，并在一分钟左右获得第一次反馈。
- 一局连续剧情控制在三至五分钟，让用户愿意看完和重玩。
- 每个关键选择关联一个可解释的知识点，用户能够说出为什么。
- 让用户练习主动表达与判断下一步，并能区分已发生的事实、可能解释和缺失信息。
- 编辑能独立更新题目、章节和知识卡，内容上线不依赖前端重新编写页面。
- 为账号、进度、内容版本和未来权益建立基础。

首版不包含支付、社交广场、真人咨询、实时 AI 聊天、开放投稿、女生追男生内容。数据模型保留对象与关系阶段字段，便于后续扩展。

## 2 用户与使用场景

首版假设面向成年中文用户，重点服务希望改善沟通的男性大学生和职场新人。正式投放前通过试用反馈确定优先人群。

| 场景 | 用户需要 | 对应体验 |
| --- | --- | --- |
| 不知道如何开始认识 | 有自然、不冒犯的表达参考 | 破冰短题和认识篇 |
| 想邀约但害怕尴尬 | 学会提出具体邀请与接受回应 | 邀约连续剧场 |
| 约会时不知道怎么做 | 理解关心、付款、节奏和边界 | 约会篇与避雷手册 |
| 经常只会讲道理 | 学习先倾听再回应 | 尴尬急救挑战 |
| 单纯想找点乐子 | 短剧情、旁白和彩蛋 | 今日题和结局卡 |

内容以具体行为和双方表达为依据。人物可以有不同爱好、作息与沟通偏好，避免用外貌、职业或单一性格标签替代人物设定。

## 4 信息架构与用户流程

网站一级导航只保留：开玩、手册、我的。管理后台独立入口。

建议页面：

- `/`：开玩首页。
- `/daily`：今日题。
- `/stories`：剧场列表。
- `/stories/:slug/play`：剧情播放。
- `/runs/:id/result`：本局结果；游客对应结果保存在本地。
- `/handbook`：手册分类与列表。
- `/handbook/:slug`：知识卡详情。
- `/me`：记录与收藏。
- `/login`：登录与注册。
- `/admin`：内容管理。

首次访问：开玩首页 → 一键试玩 → 情景 → 选项 → 后续 → 解释 → 继续或尝试另一条路线。

再次访问：开玩首页 → 继续上次剧场，或今日题 → 结局 → 收藏知识卡。

登录只在用户主动选择云端保存时出现；游客完成整章无需登录。首页不设置复杂问卷。

## 5 玩法与反馈规则

### 5.1 今日心动题

每题说明关系阶段、发生的事情和必要背景。提供两至四个选项；玩家选择后先看一小段后续，再看解说。提交后不能在同一次尝试中更换答案，重试创建新尝试。

三种题型复用同一选项组件：

| 题型 | 玩家任务 | 示例 |
| --- | --- | --- |
| 行动选择 | 选当前较合适的做法 | 她分享考试通过，怎样回应 |
| 事实判断 | 区分能确定与不能确定的事 | 她回复一个表情，哪些信息仍未知 |
| 后续选择 | 看见反馈后调整行动 | 她提出替代时间，下一句如何确认 |

信息不足时必须允许选择“还不能确定”或“先问清一个关键问题”，不能强迫猜测对方的内心。事实判断题的后续可以是旁白展示证据，而非角色新增行为。

解说卡默认只显示：本次选择评价、理由、现实中的表达参考。来源与更详细的适用条件放在“为什么”展开区。

每日题由内容后台排期，按 Asia/Shanghai 日期切换。同一天刷新不变题；完成后可以重试或进入剧场。

### 5.2 连续小剧场

章节由对白、选择、结果和结局节点构成。选择可改变人物表情、后续对白、状态与结局。各路线共享部分场景，控制制作成本。

每章约五至六次选择，既包含最初行动，也包含收到反馈后的下一步。约会篇至少覆盖积极回应、含糊回应和明确拒绝三种情况；角色反应由作者设计，并在复盘中注明其为虚构情景。

前端负责播放和即时反馈；服务端保存选择路径并校验完成状态。重玩保留之前已收集的结局，但当前局从初始状态开始。

### 5.3 正确性与行为反馈

评价对象是玩家在当前情景中的行为。每个选项标注：推荐、可接受但需看情景、容易造成误解、明显越界。评价必须附具体理由，允许同一道题存在多个可接受的选项。

采用三层判断：边界是否被尊重、行动是否符合已知背景、措辞是否自然且贴合双方偏好。明确拒绝后继续施压不能靠幽默、体贴或其他表现抵消；玩家合理表达自己的边界也可获推荐。

反馈围绕以下能力，未涉及的能力显示“不适用”，不扣分：

| 能力 | 可观察行为 |
| --- | --- |
| 事实判断 | 不把礼貌、单个表情或猜测当作明确关系意愿 |
| 双向交流 | 回应对方内容，也适度分享自己的经历 |
| 主动表达 | 提出具体、可拒绝的邀请或说出真实好感 |
| 关心与倾听 | 根据对方需要选择倾听、陪伴或建议 |
| 边界与调整 | 接受拒绝、表达自身安排，按实际反馈调整 |
| 修复 | 承认具体影响并提出可以落实的补救 |

结果页显示本局做得好的一件事、可以改进的一件事和一个可重试节点。以“已练习、建议重试”的标签体现成长，不生成综合心动值、人物价值分、MBTI配对分或现实成功率。

剧情仍可保存舒适程度、信息是否明确、约会是否确认等虚构状态，用来驱动表情与结局。它们属于作者设计，不是心理测量；结局优先检查明确拒绝和双方选择，不通过累计分数越过拒绝。

学习标签不影响账号权限和未来付费权益；付费章节解锁必须由服务端校验。

### 5.4 收到反馈后的行动规则

以下规则用于编写情景与推荐选项，属于基于知识库的教学设计：

| 情况 | 已知信息 | 推荐训练动作 |
| --- | --- | --- |
| 积极回应 | 主动延展、提出可行时间或明确愿意 | 确认一个小步骤，继续观察，不自动认定已确立关系 |
| 暂时含糊 | 说忙、礼貌简短或本次时间不合 | 本轮不连环追问；根据新信息决定是否另提一次低压力邀请 |
| 明确拒绝或不适 | 说不想发展、要求停止或明确表现不舒服 | 停止当前方向，简短接受，不安排继续说服的推荐路线 |
| 持续投入失衡 | 多次取消不重约、长期单向安排、沟通后不改善 | 保留自己的正常生活，澄清期待或停止继续投入 |

为便于把回应性原则转成一致答案，首版把已读72小时仍未回复视为明确拒绝：回应性需要通过联系体现，因此超过这一窗口就足以判断不愿发展。此情景中“结束追求”为唯一推荐答案，不再要求结合考试、工作或其他处境进行判断。

### 5.5 幽默原则

笑点来自男主脑内戏、过度紧张、措辞笨拙、场景误会与旁白。避免通过贬低女生、嘲笑外貌或羞辱单身用户制造笑点。

每个核心题至少有一个自然、实用的选项。干扰项可以搞笑，但不能全部离谱；要让用户真的需要判断。

示例旁白：“你正在申请文学奖，她只是问你吃饭了吗。”

## 7 内容规则与生产流程

### 7.1 每道题必填字段

题目标题、题型、关系阶段、沟通媒介、背景、可观察事实、关键未知、单个主要学习目标、选项、虚构后续、选项评价、理由、适用条件、下一步与停止条件、知识包、知识卡、来源、版本、审核状态。

来源记录包括机构或作者、文章标题、链接、查阅日期和支持的具体原则。来源没有说明的细节标为编辑建议，不写成研究结论。

每道题只训练一个主要动作，例如承接、邀约或澄清。情景中没有提供的细节不能偷偷进入正确答案；如需不同条件，通过显式背景变体制作。

首版不使用实时生成内容；AI 如用于辅助起草，仍需进入同一审核流程。

### 7.2 内容审核

流程：选题 → 查资料 → 写情景与选项 → 试玩 → 内容审核 → 发布。

审核检查：

- 信息是否足够让用户判断，是否把礼貌误写成喜欢。
- 是否说明具体情景，是否允许符合条件的不同答案。
- 关心是否与对方表达的需要一致，是否允许双方拒绝。
- 是否把送礼、付钱解释成对方需要回报的义务。
- 是否把持续施压、查手机、控制行踪写成推荐行为。
- 来源是否真的支持对应原则；剧情人物的反应标记为编写的后续。
- 研究、表达框架、经验建议和作者设定是否区分；长期伴侣研究不能直接变成初识场景的因果结论。
- 推荐是否包含合理的主动表达，是否误把坦率等同于冒犯、把停止追问等同于故意冷淡。
- 称赞或共情是否编造了对方未提及的经历，例如擅自认定她熬夜练习或一定很自责。
- 玩笑是否建立在共同话题和可接受的互动上；不舒服时是否允许立即停止。
- 幽默是否针对场景而非某个性别。
- 图片、字体和声音是否具备使用授权。

编辑与审核为两个逻辑角色，可由项目成员分别承担；审核完成前状态必须保持草稿。

用户可对题目提交“解释不清楚、情景不足、内容有问题”反馈；后台支持查看、处理、重新审核。

| `references/practical/实战话术编排器：从一句回复到后续分支.md` | 一轮一个目标，积极、含糊与拒绝后续 | 选择节点与分支模板 |
| `references/practical/主动表达、第一次见面与自然接触.md` | 具体欣赏、可调整约会、真实好感 | 约会篇、邀约篇，不设置肢体接触KPI |
| `references/practical/关系投入失衡：互惠判断、降级投入与退出决策.md` | 发起、兑现、修复和自己的生活 | 投入判断题、友好结束结局 |
| `references/practical/场景感、松弛感与社交校准：从接话到关系推进.md` | 共同场景、接话后分享、按反馈调整 | 搞笑对白、接话题；不复制主播人设 |
| `references/practical/万能夸人的话术技巧：真诚认可的实用指南.md` | 具体、真实的欣赏 | 赞美选择题，删去无依据的夸张推断 |
| `references/practical/为他人提供情绪价值：温暖且有效的回应指南.md` | 询问需要、记住主动分享的事、保留双方边界 | 关心与倾听题，短句化改写 |

首版不移植聊天记录分析、ChatLab、长期私人关系记忆、MBTI建档、主观人物评分，以及婚姻财产、性健康和危机咨询流程。用户个人资料维持游戏进度与收藏范围。

涉及冷读或经典搭讪体系的资料暂不直接改成攻略；原需求中的幽默与自信练习通过共同场景、真实欣赏与事实判断实现。

上述赞美与情绪回应指南注明部分内容可能由AI生成，只作为选题和句式素材。即使文件位于知识库中，也不自动拥有研究证据等级；原文中的绝对承诺、脑补细节和长篇回应须重新审核。

### 7.6 内容能力包

知识包属于内容配置，每包含主题、学习目标、资料入口、适用场景、推荐行为、常见误区、反馈模板和停止条件。首版设六包，共用原有模块，不增加六个导航入口：

| 包ID | 名称 | 重点 |
| --- | --- | --- |
| opening | 自然认识 | 现场取材、真实分享、好奇而非审讯 |
| listening | 接话与倾听 | 承接、询问需要、好消息的具体回应 |
| invitation | 邀约与表达 | 一个具体提议、真实好感、三种反馈后续 |
| date | 约会安排 | 双方偏好、守时、弹性活动和付款协商 |
| care | 关心与边界 | 具体欣赏、低压力支持、自身安排与拒绝 |
| repair | 判断与修复 | 区分事实、澄清期待、暂停、补救与结束 |

短题关联一个主要知识包，可以关联一个辅助包；连续剧场最多覆盖三包。知识包用于后台筛选、审核和学习标签。

### 7.7 证据等级与来源核查

沿用知识库的分级，但必须针对具体主张核查：

| 等级或类型 | 依据 | 使用规则 |
| --- | --- | --- |
| A | 综述、大样本纵向研究、对应领域权威指南等 | 标明研究人群、结果范围及限制；不推出个人成功率 |
| B | 设计良好的单项研究或有重复证据的过程 | 使用“可能有帮助”等限定表达 |
| C | 小样本、案例、访谈或经验观察 | 用于启发情景，不作因果结论 |
| D | 未验证的流行标签与配对框架 | 不作为唯一答案依据，首版不制作配对测算 |
| 经验建议 | 实用句式和行动框架 | 显示适用条件，不因为有理论名称就升级等级 |
| 作者设定 | 人物、剧情反应与结局 | 明确为虚构，不声称女生会统一反应 |
| 原则规则 | 双方选择、诚实表达和尊重边界 | 说明行为理由，不伪装为某项研究的量化结果 |

知识库属于二次整理，外部论文、机构指南属于原始依据。来源状态使用未核查、已核查、需复核；仅核查某篇摘要时明确记录，不能声称读过全文。无法取得原始依据时，删除效果保证或改为经验建议。

凡以研究结论作为推荐依据，相关主张和原始来源必须经过核查。纯表达建议可以按经验建议发布，但仍需内容审核。后台按主张保存等级、适用人群、局限、查阅日期与审核意见；前台将这些信息收在“为什么”中。

### 7.8 首版知识卡目录

12张卡对应六包，每包两张：

1. 从共同场景自然开口。
2. 问完之后要回应，也分享自己。
3. 她需要倾听，还是需要建议。
4. 分享好消息时，回应具体内容。
5. 把有空约变成具体邀请。
6. 分清积极、含糊与明确拒绝。
7. 第一次约会要能调整计划。
8. 迟到、付款和结束联系怎么说清楚。
9. 真实赞美与低压力关心。
10. 帮忙、送礼和自己的边界。
11. 区分事实、猜测与缺失信息。
12. 道歉、补救与体面结束。

赞美和关心参考对方主动分享的偏好与事件，不通过私下调查制造惊喜，不把昂贵礼物或大场面表白设为最高等级。用户完成相关题目后可收藏卡片，形成可查阅的学习记录。

## 8 示例题与反馈模板

### 8.1 拿包与双方边界

题目：第一次约会，她让你帮忙拿包。背景补充：你手上没有别的东西，两人正在正常交流，你也愿意帮忙。

| 选项 | 虚构后续 | 解释 |
| --- | --- | --- |
| 可以呀 | 她道谢，继续聊刚才的话题 | 顺手帮忙可以体现关心；拿包本身不等于关系确认 |
| 我不想拿 我们各自拿自己的吧 | 她收回包，交流短暂暂停 | 可以表达边界，措辞和语气影响对方理解 |
| 行 不过待会儿帮我推荐奶茶 | 她笑着说要认真挑一家 | 熟悉程度与对方反应影响玩笑是否合适 |
| 我给你拿了 你就得答应做我女朋友 | 她表示不舒服 | 帮忙不构成交换亲密关系的条件 |

### 8.2 通用反馈模板

反馈模板：

1. 剧情反馈：一两句后续，加表情或旁白。
2. 选择评价：推荐或其他等级。
3. 一句话解释：指出行为与可能影响，标出是否为经验建议。
4. 现实表达：提供一句自然示例，不要求照背。
5. 下一步：面对积极、含糊或拒绝时如何调整，必要时给停止条件。
6. 展开区：事实与未知、适用条件、依据类型、来源和关联知识卡。

这道题训练的是体贴与表达，不把“同意”和“拒绝”单独作为对错依据。

### 8.3 邀约后的三种反馈

背景：认识两周，双方聊过一个摄影展，女生主动说想了解这个展。男主提出周六下午一起看展。以下人物回应为作者设计，训练目标是根据新信息选下一步。

| 女生的回应 | 推荐行动 | 常见误区 | 搞笑旁白 |
| --- | --- | --- | --- |
| 周六不行 周日下午可以 | 确认周日是否合适，再商量地点 | 把拒绝周六当成拒绝认识 | 她给了周日，你还在给周六写悼词 |
| 最近比较忙 下次再说吧 | 接受本次不确定，不连续追问；若出现合理新信息再判断 | 立刻认定她故意试探，或追问到底哪天 | 日程表还没打开，你已经开始答辩 |
| 我不想和你约会 | 接受回应，停止追求方向 | 把拒绝解释成需要更努力证明诚意 | 本轮任务是听懂，不是开启困难模式 |

同一句邀请不保证相同反应。相同措辞面对不同背景也可能评价不同，解释应说明哪些条件改变了选择。

### 8.4 关心与赞美练习

背景：她主动提过准备面试，之后告诉你顺利通过。推荐表达可以是：“恭喜！你之前说准备了很久，现在过了，应该挺开心的吧？”接着根据她的回应继续聊。

这句话只使用她已分享的信息，不擅自补出“你一定熬了很多晚”。如果自己记不清，不把虚构细节包装成用心。对方正忙时，简短祝贺也可得到推荐，无需强行延长聊天。

小游戏可让玩家在三个表达之间选择：只有空泛夸张、回应真实细节、抢着讲自己的经历。之后展示更短、更自然的改写，训练用户关注具体内容而非背诵固定句子。

### 8.5 事实判断练习

背景：她回复“哈哈”，除此之外没有提供更多信息。题目问“现在能确定什么”。推荐选项：“她回应了这条消息，但是否想继续了解仍不清楚。”干扰项可以是“她已经喜欢我”和“她一定讨厌我”。

选择后由旁白揭示证据范围，接入“区分事实、猜测与缺失信息”知识卡。后续动作训练结束本轮或自然回到共同话题，不通过固定延迟回复制造焦虑。

## 9 UI 与交互规范

视觉方向：轻漫画、温暖、轻松搞笑。建议奶油白背景、深色正文、珊瑚色强调，具体色值在设计阶段校验对比度。

### 9.1 首页

顶部展示名称与简短定位；主体第一张卡是“开始试玩”或“继续上次”；下方展示今日题和三张剧场卡。主操作保持一个，不堆叠大量榜单、指标和弹窗。

### 9.2 游戏页

上方：返回、章节名、进度。中间：场景插画、人物表情、短对白。下方：两至四个选项。选完后展示反馈，再由用户点“继续”。

默认反馈仅展开评价、简短理由与下一步，证据详情由“为什么”按钮展开。事实判断题用同样布局，不新增复杂面板。结果页显示学习标签和可重试节点，不显示对方的心理仪表或现实成功概率。

默认关闭背景音乐。支持跳过打字效果，开启减少动画后直接展示对白。页面切出或断网时不丢失已完成选择。

### 9.3 手册与我的

手册升级为重要的系统学习模块，以“系统教程”和“随手知识卡”两个入口组织。系统教程采用主题分类、搜索与清楚的文章目录，不在列表直接铺满正文。首批前端包含20篇完整教程，六类主题为情绪认同、自然聊天、邀约与约会、氛围与靠近、误区与边界、关心与修复。推荐入门顺序为情绪认同、双向聊天、具体邀约。

每篇教程包括适用阶段、核心提示、三段正文、具体行动、原创正反例、常见误区、可展开答案的小练习与带适用说明的参考来源。肢体语言和接触内容说明当下意愿、可撤回和停止条件。人物大师或作者经验须标明为经验，不使用未核实语录或宣称保证效果。

文章使用独立路径 `/handbook/:slug`，支持直接访问、桌面侧边目录、手机折叠目录、关联教程和相关剧场入口。教程支持收藏和主动标记已读，自动打开文章不算读完。“我的练习”分别展示收藏教程、阅读记录、剧场进度与知识卡。前端试玩通过本地浏览器保存；正式版需接入账户同步和内容版本。

每张知识卡包含：一个常见问题、一个可练动作、一句示例、适用条件与来源。我的页面把学习记录显示为“练过哪些能力”，不设置人物价值排行榜。

### 9.4 可用性要求

- 优先支持手机，兼容360px至1440px以上屏幕；选项与正文不横向溢出。
- 点击目标至少44px；正文建议16px起，选项文字不得截断关键信息。
- 选项可通过键盘操作；焦点可见；不能仅靠红绿颜色表示好坏。
- 插画加载失败有占位；网络错误提供重试按钮。
- 反馈和状态变化不遮挡选项或继续按钮。
- 首版不强制横屏，不依赖悬停才能看到解释。

初始素材建议：1位男主、3位女角色、每人3种表情、4个共用背景。数量为制作预算，角色设定由内容阶段完成。

## 10 留存与传播

留存围绕短体验、连续剧情和学习收获，不用连续签到惩罚强迫回访。

| 机制 | 首版安排 | 验证方式 |
| --- | --- | --- |
| 今日一题 | 运营排期，同日固定 | 次日与七日回访 |
| 继续上次 | 首页直接恢复 | 续玩率 |
| 另一条路线 | 结局提示未发现内容 | 重玩率 |
| 换个背景再试 | 同一题改变熟悉度或明确偏好，共用组件 | 背景变体的完成率与误判变化 |
| 收藏知识卡 | 反馈中直接收藏 | 收藏率与阅读量 |
| 结局收集 | 我的页面显示已解锁结局 | 完成章节数 |
| 分享卡 | P1，本地生成搞笑称号卡 | 分享操作与回流 |

称号表达具体游戏行为，例如“建议输出机”“邀约终于具体了”。避免贬损称号。分享内容不包含用户名以外的个人信息，昵称默认也不展示。

分享卡示例：今日称号——建议输出机，倾听功能正在升级。

背景变体使用题目已有数据字段，首版30道题中安排至少三组对照题，每组两道。例如“双方经常互相接梗”和“初次交流、不知道是否接受打趣”。用户在复盘后可挑战另一背景；不能宣称由一组题识别其真实人格。

## 11 技术架构与数据

当前实现目录、启动命令见项目根目录README；后端接口与已实现的权限、版本、幂等规则见 `docs/API.md`，服务器配置见 `deploy/README.md`。后端已提供内容版本、账号、云端存档、收藏/已读、游客合并、每日排期、反馈与管理操作接口。本机验证以H2数据库为主，真实PostgreSQL、服务器负载与Docker部署另做验收，不因API完成而标记上线检查全部通过。

### 11.1 技术选型

| 部分 | 方案 |
| --- | --- |
| 用户前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia |
| UI | Tailwind CSS与自定义组件 |
| 管理前端 | Vue 3，复用类型定义，独立入口 |
| 服务端 | Java、Spring Boot、Spring Security、REST API |
| 数据库 | PostgreSQL，迁移脚本管理结构 |
| 部署 | Linux、Nginx、Docker Compose |
| Redis | P1按缓存与会话需求增加 |
| AI服务 | 首版不接入 |

知识库通过内容制作流程取用：参考选题 → 原创改写 → 主张核查 → 试玩审核 → 发布JSON。运行时不安装或执行该Skill的脚本，也不把完整知识库自动发送给模型。前后端继续采用现有方案。

版本在开发开始时选兼容的稳定版本，并记录到依赖锁定文件。前后端各自构建和发布，域名统一，Nginx把`/api`转发到服务端。

### 11.2 部署关系

```text
浏览器
  └─ Nginx
      ├─ 前端文件与公开图片
      ├─ /admin 管理页面
      └─ /api Spring Boot
                └─ PostgreSQL
```

单服务器起步，4核8GB作为规划配置。沿用当前容量判断：十万累计用户可用十万次请求近似，而Java多线程能够并行分担，因此此配置可覆盖十万以内用户。注册量超过十万再启动服务拆分；上线前用压测检查接口和资源配置。

### 11.3 剧情运行与存档

进入章节时加载当前发布版本的剧情数据，点击选项在前端即时执行。图片按需加载并预取下一幕。重要选择后保存本地进度，再异步同步云端。

服务端根据节点ID、选项ID与内容版本校验路径；学习标签和结局根据已发布配置重放得到，不信任客户端自行声明的结果。重复请求通过局ID与序号去重。存档与内容版本绑定，保留旧版供已有局继续；紧急下架内容停止新局，并展示旧存档处理提示。

游客保存到浏览器本地，清理浏览器后可能丢失；我的页面说明这一点。多设备首版使用最近一次用户明确保存的进度，冲突时提示选择，不静默覆盖。

| Review | 内容版本、编辑、审核、意见、操作时间 |
| Feedback | 题目、问题类型、描述、处理状态 |

剧情使用结构化JSON存储节点和分支，用户与运营数据使用关系表。JSON在发布前验证类型、节点引用、可达性与结局。首版限制循环分支，防止用户无法结束。

题目引用SourceClaim ID，可共享来源但分别记录主张与限制。人物设定只保存作者定义的兴趣、偏好与边界，不包含人格诊断或“可攻略程度”。明确拒绝标记优先于普通剧情状态；不允许用其他状态变化自动解锁继续施压的推荐路线。

### 11.5 接口范围

首版覆盖公开内容列表和详情、今日排期、账号登录退出、开始一局、提交选择、恢复进度、结果、收藏、反馈及内容后台。接口文档定义请求字段、权限、错误码和幂等行为。

登录采用同域安全Cookie；HTTPS上线。管理接口鉴权，密码哈希保存，限制登录尝试，防止公开内容接口读取草稿。客户端显示错误时不暴露堆栈或数据库信息。

## 12 性能与运维验收

以下为测试目标，尚未验证，不作为已达成结果：

| 项目 | 首版目标 | 测试条件 |
| --- | --- | --- |
| 前端选择反馈 | 点击后100ms内有可见反馈 | 已加载剧情，目标手机设备 |
| 首屏主要内容 | 2.5秒内显示 | 明确设备、地区、网络和首次访问条件 |
| 普通读接口 | P95低于300ms | 约定数据集和持续负载 |
| 存档接口 | P95低于500ms | 含数据库写入，不含公网往返 |
| 图片资源 | 优先WebP或AVIF，提供尺寸 | 首章素材预算与慢网测试 |
| 稳定性 | 无未处理错误导致存档丢失 | 断网、重试、重复提交测试 |

容量验证从100个在线模拟会话、平均每10秒一次API请求开始，约10 RPS；逐步提高并记录CPU、内存、数据库连接与响应延迟。测试结果用于检查配置，而扩容时机按累计注册量规则执行。

运维要求：HTTPS、结构化日志、健康检查、持久化数据库目录、每日备份、上线前完成一次恢复演练、发布回滚记录。数据库不开放公网访问。

## 13 产品指标

埋点不记录密码、完整自由文本或个人聊天内容。事件包含内容ID、版本、局ID与时间，用户标识尽量匿名。

| 指标 | 定义 |
| --- | --- |
| 试玩启动率 | 点击试玩的独立访客数 ÷ 首页独立访客数 |
| 首局完成率 | 首局完成用户数 ÷ 首局开始用户数 |
| 剧场重玩率 | 完成后再次开始同章节的用户数 ÷ 完成用户数 |
| 次日留存 | 首次游玩日的用户中，在次日再次游玩的比例 |
| 七日留存 | 首次游玩日的用户中，在第七日再次游玩的比例 |
| 有用反馈率 | 选择有用的反馈数 ÷ 全部回答有用性问题的反馈数 |
| 内容问题率 | 被反馈有问题的尝试数 ÷ 全部尝试数 |
| 重试改进率 | 同版本同背景下，重试由误解或越界选项改为推荐或可接受的用户数 ÷ 对应重试用户数 |

日期均按Asia/Shanghai统计。游客跨浏览器无法可靠去重，数据面板说明这一限制。事件最少包括：首页访问、开始、选择、完成、重玩、知识卡阅读、收藏、反馈。

首轮观察目标建议：首局完成率60%以上、重玩率20%以上、回答者有用反馈率70%以上。属于待验证假设；样本不足时同时报告人数，不凭百分比决定大规模投入。

重试改进率只表示游戏内选择变化，不能宣称用户现实追求成功率提高。背景变体分开统计，避免将情景改变导致的答案变化当成学习效果。P1可增加同一知识点的新题复测，进一步区别记住答案和理解条件。

## 14 分阶段开发计划

周期假设：一名全栈开发，内容与素材能同步提供；约六至八周。人力、美术和审稿进度变化会影响日期，以下使用相对周次。

| 阶段 | 工作 | 交付 | 通过条件 |
| --- | --- | --- | --- |
| 第1周 产品与设计 | 定内容能力包、行为评价、页面与示例 | 六包定义、低保真页面、6道题和1章脚本 | 三种题型与反馈分支走通，内容可解释 |
| 第2至3周 核心玩法 | 前端、剧情引擎、本地存档 | 可玩的原型 | 可到达全部结局，刷新可恢复 |
| 第3至4周 服务端 | 账号、内容API、云存档、收藏 | 前后端联调版本 | 权限、重试、冲突处理正常 |
| 第4至5周 内容后台 | 编辑、知识包、主张核查、预览、排期与版本 | 可运营版本 | 研究依据未核查时阻止按研究结论发布，编辑可独立上线章节 |
| 第5至6周 内容与验证 | 补齐题库、美术、移动端与负载测试 | 30题、3剧场、12卡、检查记录 | 内容全审核，主流程通过 |
| 第7至8周 小范围上线 | 部署、备份恢复、试用与修复 | MVP与反馈列表 | 可监测、可回滚，阻塞问题清零 |

优先落地一章端到端闭环，再批量制作其余内容。P1和商业功能不挤占首版主流程。

建议项目目录：

```text
LoveLab/
  docs/       PRD、设计、接口和内容规范
  frontend/   用户网站
  admin/      内容后台
  backend/    Spring Boot
  content/    初始剧情与知识卡
  deploy/     部署配置与运维说明
```

## 15 上线检查与后续扩展

上线必须完成：

- 游客开始、选择、解释、结局、重玩完整闭环。
- 登录、进度迁移、收藏与恢复流程验证。
- 内容路径检查、来源审核、30道短题与3章内容准备。
- 六个知识包和12张知识卡完成；每道题有一个主目标与可解释评价。
- 积极、含糊、明确拒绝分支通过；学习标签不展示为现实概率。
- 信息不足时可保留判断；合理拒绝可获推荐；共情与赞美不编造事实。
- 至少三组背景对照题完成；适用条件变化能在解释中看到。
- 改编资料保留来源记录和许可声明，研究主张记录核查范围。
- 手机窄屏、键盘操作、减少动画、素材失败处理。
- 断网、重复点击、存档重试、旧版本与下架处理。
- 管理权限、草稿隔离、日志、备份恢复和回滚演练。
- 指标采集与内容问题反馈可用。

商业扩展方向：免费基础剧情，付费专题、更多章节、学习计划与深度复盘。等用户完成率、回访和内容反馈稳定后，再设计订单、权益、退款与客服流程。首版不预设收费价格。

暂定事项：登录方式按用户名密码闭环；素材按轻漫画预算；中国大陆部署区域与域名在上线准备阶段确认。核心玩法确定后再决定P1排序题与分享卡的开发时间。
